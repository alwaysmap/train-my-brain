- `--hue 400` rejected (exit 2) as expected.
- `./serve.sh --port 1314` started a real server (HTTP 200 on probe) and wrote `.hugo.pid` (21064).
- `./stop.sh` killed the recorded pid and cleaned the pidfile.
- `npm run build` produces `train-my-brain.zip` v0.3.0 (63.7 KB, 41 files). Archive includes every v0.3 surface directory.

## What still needs live-plugin validation

Nothing below was exercisable from inside this Claude Code session because the plugin isn't installed in the session itself. Each needs a real install + interactive run:

1. `/tmb:create` full pipeline against a real interview.
2. Agent dispatch through the Agent tool targeting `tmb-designer`, `tmb-module-builder`, `tmb-reviewer`. Open question: does Claude Code's plugin agent discovery pick up `agents/<name>.md` with the current `plugin.json` shape, or do the agents need explicit declaration beyond `"agents": "./agents"`?
3. Parallel dispatch of N module-builders in a single assistant turn. Research said cap is ~10 concurrent; our design assumes this but we haven't observed it.
4. tmux-detached server path inside the `/tmb:create` orchestrator. `nohup &`/`disown` are known to fail under Bash-tool `--die-with-parent`; tmux is the documented workaround but we haven't run it from inside a skill body yet.

6. `/tmb:add-module --insert-at-position K` weight-shift flow.
7. `/tmb:rebuild-site` against a v0.2-shaped curriculum — needs to refuse cleanly.
8. `check-hugo.sh` install offer path — we verified the detection path but haven't run the `brew install` branch because Hugo is already present.
9. Windows-side testing of `.ps1` scripts. None of the PowerShell paths were exercised; they mirror the bash scripts structurally but need someone on Windows to confirm.

## Learnings worth carrying forward

**Plugin layout conventions are at plugin root, not inside `.claude-plugin/`.** The origin brainstorm assumed `.claude-plugin/commands/` and `.claude-plugin/agents/`. Research against the Q1 2026 docs and this repo's own `skills/` placement corrected that: `commands/`, `agents/`, `skills/`, `references/` all sit as siblings to `.claude-plugin/`. Any future plugin should start from this understanding.

**Plugin manifest can declare surface paths explicitly.** `plugin.json` accepts `"commands": "./commands"`, `"agents": "./agents"`, `"skills": "./skills"`. Not required (convention-based discovery works) but makes the plugin's surface reviewable at a glance. Added to v0.3 manifest.

**Build pipeline drift between `scripts/build.js` and `.github/workflows/release.yml`.** Both hard-code the includes list. They must change in lockstep or the local build diverges from the released artifact. Flagged this as a risk in the plan; addressed by touching both files in the same commit. No lint check yet — worth adding one eventually.

**`Bash run_in_background` uses `--die-with-parent`.** Documented Claude Code behavior: `nohup ... &`, `setsid`, `disown`, trailing `&` all fail to outlive the parent Bash tool call. tmux is the documented workaround. In this smoke test we used `run_in_background: true` and got a process that outlived the tool call by several seconds — enough for our probe — but the long-term detachment story still depends on tmux. For v0.3 we teach the orchestrator to try tmux first and fall back to telling the user to run `./serve.sh` themselves.

**Parallel agent dispatch is plausible but untested at scale.** Claude Code caps at ~10 concurrent subagents in one assistant turn. For TMB's 5–9 module curricula, this is fine. The cap should be made visible if we ever grow the skill beyond those numbers.

**`skills/<plugin-name>/` would create `/<plugin>:<plugin>` as the command name.** Because the plugin namespace prefix is the plugin's `name` field, a skill at `skills/tmb/SKILL.md` under plugin name `tmb` becomes `/tmb:tmb` — awkward. We renamed the bare-pointer concept to `skills/help/SKILL.md` → `/tmb:help`. Rule of thumb for future plugins: don't name a skill the same as the plugin.

**`--kind` on `hugo new` is redundant when the path already routes.** `hugo new content/modules/NN/index.md` picks up `archetypes/modules.md` automatically. The explicit `--kind modules` flag added nothing; stripped during planning.

**Archetype frontmatter is the reviewer's contract.** Extending the archetype with TMB-specific fields (`driving_question`, `concepts`, `contrast`, `prior_ends_with`, `next_expects`) lets the reviewer validate adjacency and pedagogy without parsing prose. Worth keeping this pattern — extend the archetype when you want structured validation.

**Shared references at plugin root avoid per-skill duplication.** Moving `elicitation.md`, `curriculum-design.md`, `markdown-gotchas.md`, `hugo-site.md` from `skills/tmb/references/` to plugin-root `references/` lets every skill and agent cite them by relative path. Copy-per-skill would have tripled maintenance.

**Deterministic operations belong in shell scripts, not prose.** The `scripts/scaffold-site.sh` approach (embedded heredocs for layouts/CSS/archetype) replaces the v0.2 pattern of the skill itself writing files via `bash_tool` heredocs in its prompt. The script is unit-testable; the prompt-driven approach was not.

## Risks still tracked

From the plan's Risks & Dependencies table, these remain open post-implementation and depend on live-plugin testing:

- Claude Code plugin convention divergence (addressed by Unit 1 but not yet empirically verified by actually installing the plugin and invoking `/tmb:help`).
- tmux-detached server UX when tmux is not available.
- Reviewer AI-prose regex false-positive rate — tunable during real runs.
- Cross-platform script parity (Windows side).
